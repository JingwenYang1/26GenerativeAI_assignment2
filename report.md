# Indie Game Pitch Email Generator

## Business Use Case
This project automates the first draft of pitch emails that indie game developers send to investors and publishers. The user is a solo developer or a small studio founder who has a clear game concept but has limited time and limited experience in business writing. The system takes a short description of a game, including genre, setting, and key features, and produces a professional pitch email that introduces the project and invites further discussion. The main value is to reduce the “blank page” problem, so the developer can spend more time refining the draft instead of starting from zero.

## Model Choice
The prototype uses Gemini 2.5 Flash through the Google AI Studio API. It was chosen because it is fast, low-cost, and good enough at following instructions for structured writing tasks like business email generation. Earlier attempts with Gemini 2.0 Flash did not work because the model is no longer available to new accounts, and Gemini 1.5 Flash was not accessible under the current API project. Therefore, 2.5 Flash was the most practical option that is both available and affordable.

## Baseline vs Final Design
The baseline system instruction asked the model to write a "compelling, professional pitch email around 200 words" with a hook, a clear description of the concept, a market angle, and a call to action. This version produced fluent output, but several problems appeared across the five evaluation cases. The model invented game titles that were not provided, used markdown formatting that would not display properly in a real email client, and added placeholder signatures automatically. It also created specific gameplay mechanics when the input was vague. In addition, it directly mentioned reference games like Persona and Danganronpa in the email body, which in a real pitch may sound like imitation instead of inspiration.

Two prompt revisions were applied to address these issues. Revision 1 added explicit constraints, including not inventing titles, not using markdown formatting, not fabricating gameplay mechanics, and not claiming nonexistent prototypes. It also fixed the email signature to a consistent identity. Revision 2 further improved the system by tightening the tone, forbidding the naming of reference games, and requiring the model to acknowledge early-stage concepts instead of inventing details. It also expanded the no-fabrication rule to cover design documents and pitch decks. The final version produces emails that are more grounded, no longer expose source-game names, and handle abstract inputs by clearly stating that the project is still in development instead of adding unnecessary details.

## Where the Prototype Still Fails
The most consistent problem across all three versions is length control. The baseline asked for around 200 words, Revision 1 changed the range to 150 to 200, and Revision 2 further narrowed it to 150 to 180. However, all versions still exceeded the target length. This shows that soft length limits in prompts are not reliably followed and may need to be handled in code, such as by truncation or post-processing. The model also still adds small invented details when the input is very limited, especially in describing tone and atmosphere. Although this behavior is reduced, it is not fully eliminated, so human review is still required before sending the email.

## Deployment Recommendation
This prototype should not be deployed as a fully automated system. It is more suitable as a draft-generation tool within a human review workflow, where the developer uses the output as a starting point and edits it before sending. The system reduces the blank-page problem and provides a clear structure, which is useful in practice. However, because of the remaining hallucination risk and weak length control, using it without supervision may lead to unprofessional results. With a simple review step, this workflow is still worth adopting.
